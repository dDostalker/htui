# htui 边界文档（Boundaries & Scope）

终端的显示能力存在局限性，为保证htui不会无休止的追赶Web协议，并保证能够将已知范围内做到最好，故通过本文档定义 htui 行为边界。

---

## 1. 目标

**让TUI的编写和Web一样简单**：过去的TUI框架中，需要学习众多的框架的API，并且TUI的显示上限也存在不足，为了降低学习成本，并实现能最大限度的提高TUI的上限，会 HTML / CSS / JS 的人，不学任何 TUI 框架，
就能在终端里写出带布局、交互和脚本的界面。是htui 用 Rust 写终端 UI 的又一种方式。

当然HTUI并不是银弹，在响应速度、编译体积、运行内存等方面是完全劣于其他TUI框架的，这是换取简单和美观的必然代价。

## 2. 核心承诺

Htui的目标是削弱个人学习的心智负担，复用自身HTML知识，对于LLM，降低其所需要的学习库成本，直接使用其自身HTML知识储备，以下是Htui的核心能力，是Htui的实现目标和标准：

1. **HTML标签与语义**：确保行为尽可能与浏览器标准一致，尽可能的降低Web开发思想转移到Htui的摩擦。具体标准参考见AIM/HTML
2. **DOM API与事件模型**：确保行为尽可能与浏览器标准一致，但由于终端的本身功能的局限性和实现的架构不同，为了减少不一致性，DOM API的实现会相对保守，但承诺不会添加Htui专有API，具体参考AIM/DOM。
3. **CSS**：尽可能遵循W3C标准，但由于终端显示有限，只实现常见一类快照的CSS功能，确保实现功能时不存在切换心智的阻碍，具体参考见AIM/CSS。
4. **ECMA**：ECMA的实现由Boa完成实现。
5. **交互**：Htui鼠标交互基本继承浏览器模型，点击、hover、拖选、剪贴板等、键盘交互提供基本功能，若特定键需使用JS自主实现。
6. **调试**：调试提更基本调试API，可进行无头打印指定显示界面。且日志可追踪。
6. **无头测试**：核心逻辑不依赖真实终端，提供接口，可以通过json数据实现无头操作终端内容。

## 3. 拒绝清单

以下内容**永不进入**实现范围，除非未来版本中变化：

| 拒绝项 | 理由 |
| ------ | ---- |
| CSS 动画 / 过渡 / `transform` / `opacity` | 终端无时间轴与像素语义|
| 完整 CSS 如grid |终端显示无法完美支持，只会导致更大的认知负担 |
| Htui直接访问数据|Htui不实现浏览器，数据的传输只通过注册`mem://`进行传递,过多的功能会导致风险|
| 像素级渲染（除 `<img>` 光栅化） | 终端是字符网格，像素渲染偏离使命 |
| 浏览器 devtools | 使用配套自带工具 |
| 多文档并行 / 窗口管理 | 单文档会话是当前模型 |
| 无障碍 / 屏幕阅读器 | 不做承诺 |
| 触摸 / 移动端 | 不做承诺 |

## 5. 与浏览器的对齐层级

- **完全对齐（必须）**：文本布局与换行、CSS 级联、盒模型、事件语义等基本概念。
- **有意识偏离（可接受）**：渲染是字符网格而非像素；行内布局为近似；
  字体以"单元格"为单位；
- **不承诺（明确告知用户）**：视觉像素、动画、完整 Web API、媒体查询。
  不承诺产生明确报错，而是静默渲染。

## 6. 性能边界

- 交互：单帧增量渲染目标 < 5ms （区域重绘路径）。
- 动态页面（`setInterval` 刷新）：刷新间隔 ≥ 100ms 时不应掉帧。
- 每次渲染线程全量重绘是最后手段，任何新特性不得默认走全量路径。

## 7. 功能决策准则

新增功能（标签、CSS 属性、JS API、交互）时，逐条对照：

1. **使命**：服务于"终端 Web 开发"吗？如果是纯 Rust 库便利性，拒绝。
2. **对齐**：能按浏览器语义实现吗？不能则明确偏离并文档化，绝不"半对齐"。
3. **性能**：最坏情况下每帧成本是否在 §7 预算内？
4. **可测**：能写无头测试吗？不能则重新设计。
5. **拒绝清单**：是否已被 §3 覆盖？被覆盖则拒绝。
6. **维护成本**：可维护性，新子系统（如完整 grid）若无持续投入计划，保持预留状态。
